# Stremio Server WebAdmin 2.0.22-dev

## Summary

Development validation release integrating upstream Stremio Server/Core 1.6.20 into the WebAdmin platform.

This release integrates upstream Server/Core changes from 1.6.16 through 1.6.20 while preserving the fork-specific WebAdmin, VPN, DNS, GPU/transcoding and deployment architecture.

2.0.22-dev is intended for validation before promotion to a production release.

## AUTO-only transcoding and WebAdmin

- Stremio remains authoritative for Direct Stream/copy vs transcode and output codec selection.
- WebAdmin no longer exposes manual Copy/H.264/HEVC/VAAPI/NVENC/CPU execution selectors.
- AUTO discovers VAAPI/NVENC capability without forcing re-encoding; no valid GPU falls back to the normal Stremio/CPU path.
- WebAdmin telemetry is normalized to AUTO even when an upgraded installation still contains legacy persisted profile/codec values.
- Legacy execution keys remain readable for upgrade compatibility but are no longer authoritative and are read-only in the UI.
- H.264/HEVC hardware self-tests are capability diagnostics only.
- Equivalent HLS workloads are deduplicated so compatible requests share the main video FFmpeg/HLS job; subtitle extraction remains independent.
- Transcode job/workload cleanup is hardened against lifecycle races.
- Media probing now preserves HDR-relevant profile, pixel-format/bit-depth and colour metadata. This does not by itself change COPY/transcode policy: the current HLS client contract declares codec/width but no explicit HDR/DoVi capability, so HDR is not blindly forced through H.264 without a validated tone-mapping policy.

### Validation evidence to date

On the Intel Iris Xe VAAPI development environment, `/transcode.json` reported AUTO with `/dev/dri/renderD128`. Real playback preserved Stremio's `-c:v copy` decision instead of forcing a GPU encode. A direct H.264 VAAPI encode produced 300 frames at 1920x1080 successfully, and an end-to-end `Converter` workload with a core `transcode` decision produced HLS/fMP4 (`master.m3u8`, `index.m3u8`, `init.mp4`, `seg*.m4s`) through `h264_vaapi` at 640x360. The 12-second workload completed 360 frames at about 8.28x realtime. Final release validation still requires a real playback for which Stremio itself requests video transcoding; synthetic/runtime validation must not be used to force that media decision.

## Upgrade notes

Before upgrading:

    sh scripts/backup-before-upgrade.sh

Preserve the existing `.env` and all persistent Docker volumes.

After extracting the new deployment package:

    sh scripts/check-env-upgrade.sh
    sh start.sh config
    sh start.sh

Do not use `docker compose down -v` during a routine upgrade or rollback.

## AUTO runtime validation

Validated on Intel Iris Xe with `/dev/dri/renderD128`: AUTO discovery reports VAAPI capability while keeping `videoCodec=null` at idle. Real HEVC playback with Stremio selecting `-c:v copy` preserved COPY, and WebAdmin reported CPU audio conversion rather than VAAPI video encoding.

The converter now separates playback decisions from execution capability. When the core requests video transcoding, AUTO routes the existing H.264 transcode target through detected VAAPI encode, NVENC encode, or libx264 fallback. GPU discovery does not force hardware decode and never promotes COPY to TRANSCODE.

Launcher validation confirmed `./start.sh --help` has no setup side effects. Normal `start.sh` startup exports the discovered render node to the VAAPI Compose overlay; direct Compose invocation bypasses launcher discovery and must provide `VAAPI_DEVICE` in its environment.


The transcoding capability API uses AUTO semantics: backend/encoder self-tests are diagnostic capability data, not selectable execution profiles. It exposes `detectedBackend` and `availableForAuto` rather than the legacy `recommendedProfile` / `selectable` contract.
